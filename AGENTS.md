# Development-agent instructions

- Product name: **MatterDraft Studio**, shortened to **MatterDraft**. Use application/product terminology in current UI, packages and documentation. Keep historical evidence and compatibility identifiers exact; do not infer production qualification or court approval from branding.
- Read `README.md`, `docs/PROJECT_CONTEXT_AND_HANDOFF.md` and `docs/ACCEPTANCE_TESTS.md` before changing architecture.
- Stack: Vue 3 + TypeScript + Tauri 2; local Python FastAPI/PyMuPDF/Tesseract sidecar; SQLite.
- PDF migration direction (18 November 2026): use Rust `pdf_oxide` for new PDF workloads; do not expand PyMuPDF usage. Build and verify replacements in stages, then switch the shipped PDF workflow from Python to Rust in one cutover only after complete current-behavior, fidelity, original-integrity, failure, storage and packaging checks. Keep Python as the independent default/reference until then. Preserve the Python deterministic page map as the golden contract until exact Rust planner parity, and preserve working-copy/vault boundaries. Never remove functionality merely to remove the dependency. Prioritize PDF-03/06/07/08; keep their acceptance gates open until verified. See `docs/RUST_PDF_SINGLE_CUTOVER_PLAN.md`.
- Backend destination (17 November 2026): Rust backend replacing Python incrementally, not merely Rust called permanently from Python. Preserve existing HTTP/API semantics during migration; one owner for database writes, migrations, revisions and jobs at each stage. Port the deterministic planner only with exact cross-language fixture parity. See `docs/RUST_BACKEND_MIGRATION_AUDIT.md`.
- Rust requirement coverage: use `docs/RUST_REQUIREMENTS_MATRIX.md` to map original brief and PRD features to migration tickets. Preserve current capabilities and separately complete missing requirements; a port of partial Python behavior does not close the full feature. Deferred signing/sharing/conversion scope remains recorded, never counted as implemented. Do not drop features to fit PDF Oxide capabilities.
- **Never describe court rules as nationwide or court-approved unless exact scoped official sources and an advocate's approval exist.** The `delhi-hc-illustrative` pack is explicitly NOT legally approved.
- Preserve imported originals; all page edits operate on working copies. Never infer that OCR text or a scanned signature is legally verified.
- PDF index, bookmarks, volume page numbers, CSV ranges and combined offsets must all derive from one deterministic page map. `backend/app/engine.py` remains the reference until an exact-parity Rust planner becomes authoritative at cutover. Add Python reference and Rust parity fixtures for every new volume/index rule.
- Keep backend processing UI-independent. Avoid adding cloud dependencies for core features.
- Python tests: `cd backend && python -m pytest -q`. Use the configured backend virtual environment; record current results in `docs/ACCEPTANCE_TESTS.md`.
- Frontend: `cd frontend && npm run build && npm run test`; install dependencies with `npm install` if missing. Browser checks use `npm run test:e2e` with synthetic data. Format frontend source/configuration and browser tests with `cd frontend && npm run format`; use `npm run format:check` to verify formatting without rewriting files. Prettier is a pinned development dependency.
- Rust/Tauri: native build requires matching PyInstaller sidecar in `frontend/src-tauri/binaries/`; create via `python backend/scripts/build_sidecar.py`, then `cd frontend && npm run tauri:build -- --bundles app` on macOS. Local Apple Silicon builds have been verified; consult the acceptance log for remaining target-device checks.
- First priority: real Mac/Windows compile, browser UI runtime verification, native export/save testing. Do not infer those tests passed.
- Work with synthetic files in `samples/`, not actual confidential matters. Source hashes and signed documents require extra caution.
- For new implementation tickets, carry authorized work through implementation, verification and handoff in one pass; do not stop after scaffolding. Mark a ticket complete only when its stated acceptance checks pass.

- UI work must use the supplied scoped design as the layout source. Preserve capabilities and data, not the legacy layout. Verify rendered screenshots against the reference viewport before marking a UI task complete; do not defer visual fidelity to later feature tasks. See `docs/DESIGN_PHASE02D_UI_CORRECTION.md`.

- Prefer unstyled Reka UI primitives for suitable shared interactions. Reuse `components/ui` wrappers and `as-child` to retain the supplied layout, existing DOM styling hooks, tokens, fonts and spacing. Preserve required selections, workflow guards and native control behavior; do not add a theme/reset or replace native controls solely for library coverage. Verify keyboard behavior and rendered light/dark layouts after adoption.

- Rust backend transport decision (17 November 2026): use a UI-independent Rust core linked into Tauri and thin direct commands (`invoke`), not a Rust HTTP server. Keep Python untouched as the separate reference/default until parity. `./dev-rust.sh` selects native debug IPC mode; no Python store access or silent delegation. Older HTTP/delegation proposals are superseded.

- Rust responsiveness: direct IPC commands must dispatch blocking SQLite/filesystem/PDF/CPU work to bounded in-process worker threads, including store initialization. Never run that work on the UI thread or block an async executor. Rust mode must not spawn a Rust HTTP server, daemon, Python service or PDF worker child process. Preserve single-writer transactions; caller timeout is not cancellation and must not trigger automatic mutation retries. Qualify native input/render responsiveness separately from the known repaint issue.
