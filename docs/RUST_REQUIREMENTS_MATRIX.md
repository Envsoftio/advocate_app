Audit: 17 November 2026. Sources: `originalrequirement.txt`, root `MatterDraft_Project_Context_and_Handoff.md`, `IMPLEMENTATION_TASKS.md`, `ACCEPTANCE_TESTS.md`, and the three `PRD_*.md` specifications. This is the migration coverage register, not a completion certificate. The original brief remains unchanged as source evidence.

## Scope and acceptance rules

The owner now selects a Rust desktop backend with PDF Oxide as the preferred PDF engine, superseding the original Python/PyMuPDF implementation choice. Preserve Vue/TypeScript/Tauri and offline local document processing. Rust owns application workflows; PDF Oxide is a PDF library, not a database, OCR recognizer, scanner driver, Office suite, legal rule source or cloud portal.

Two independent gates apply to every row:

- **Parity:** Rust preserves the currently supported behavior, including refusals, failure recovery and saved-data compatibility.
- **Requirement completion:** the full agreed feature passes its own acceptance, including missing functionality and native/legal review. Porting partial Python behavior does not complete an original requirement.

The original requirement rows record the baseline and target scope. See the [current Python-to-Rust coverage](#current-python-to-rust-coverage--19-november-2026) for implementation and parity status.

## Definition of completed Rust migration

Every non-deferred row must link to Rust implementation, applicable synthetic fixtures, executed parity and feature acceptance results, and native target evidence. Deferred items remain listed with their owner decision; no implicit closure. Rust must own all desktop API/storage/jobs/planning operations with no required Python/PyInstaller/PyMuPDF runtime path before claiming a Rust backend replacement. Existing 384 backend tests and packaged-worker smoke are evidence for the current hybrid system only.

If PDF Oxide cannot meet a requirement, record the reproducible gap and keep the existing working operation during migration. Implement a reviewed Rust extension or separately assessed local native component; do not delete a feature, substitute a weaker behavior, or claim upstream API availability proves fidelity. Keep Tesseract as the current recognizer unless a separate evaluated replacement is selected.
