# Rust PDF single-cutover plan

Owner decision: 18 November 2026. Replace the shipped Python PDF processing path with a Rust-owned path in **one release cutover**. Keep the Vue layout and user workflow. Implement and test the replacement behind the existing opt-in Rust mode before changing the default. No PDF operation is considered migrated for users until the complete current PDF workflow passes the release gate below.

## Scope and boundary

- Rust owns PDF admission, inspection, rendering for backend previews, search, page edits, OCR orchestration, build planning, PDF writing, validation, export, jobs, revisions and storage transactions. The UI-independent core is linked into Tauri through thin direct `invoke` commands. It runs blocking work in bounded in-process workers; there is no Rust HTTP server, Python delegation or PDF worker child process in Rust mode.
- `pdf_oxide` is the primary Rust PDF parser/writer. Tesseract may remain the local OCR recognizer, but Rust must own its scheduling, provenance, searchable-layer insertion and failure handling. If PDF Oxide lacks a needed operation, first implement and qualify a Rust extension around it. If that cannot preserve the current behavior, block cutover and record the gap; a library limitation cannot remove a current feature.
- The Python backend remains the independent reference/default while the Rust implementation is built. Its deterministic page map in `backend/app/engine.py` is the golden contract until a pure Rust planner matches exact cross-language fixtures. One map must then drive index rows, bookmarks, volume labels, CSV ranges, links and combined offsets.
- Imported originals stay byte-for-byte immutable. Every PDF byte edit creates a working-copy revision; private review records retain their current revision-anchored persistence contract. One Rust owner handles database writes, migrations, jobs, vault files, revisions and published builds after cutover. No Rust operation opens or mutates a Python-owned store during development.
- The cutover targets **all currently supported Python behavior**, including its explicit refusals and review warnings. Missing or deferred product requirements in `RUST_REQUIREMENTS_MATRIX.md` stay open; a faithful port does not imply they are implemented or legally approved.

## Parity method

1. Freeze a synthetic baseline from the Python default: request/response and error fixtures, page-map JSON, input and output hashes, rendered pages, native text, links, outlines, labels, CSV/ZIP inventories, history/audit records and job transitions. Keep protected-store fixtures disposable. Record existing Python defects separately so the Rust path does not silently change behavior or inherit unsafe output.
2. Drive the same fixture corpus through separate Python and Rust stores. Compare exact application contracts and deterministic maps; normalize only documented nondeterministic IDs/timestamps. Compare PDF semantics and pixels with independent readers, not binary PDF equality alone. Run adversarial signed/encrypted/malformed, rotated/cropped, OCR, Unicode, large-file and failure-injection cases.
3. Keep the Python baseline running in CI while Rust packages are implemented. A Rust failure must be visible and must never retry a mutation through Python. Repair mismatches or document an intentionally reviewed contract change before the cutover gate.
4. Run Rust core, Tauri, Python reference, frontend unit/build/format, browser light/dark journeys and real native journeys **after the final source edit**. Use synthetic files only. Record exact commands/results in `ACCEPTANCE_TESTS.md`; a historical pass is not a pass for the final build.

## Single cutover gate

Change the default backend and remove Python/PyInstaller/PyMuPDF from the shipped runtime only when **all** of these are true:

1. Every currently supported PDF action and dependent storage/job/export route has a Rust implementation or an explicitly reviewed equivalent with matching UI contract. No ordinary workflow returns the Rust pilot's 501 or exact-sample-only 422. `workflow_ready` becomes true only after this check.
2. The Rust planner matches the Python golden page maps exactly across volume, index growth, numbering, supplement, variant and link fixtures. The generated PDFs, CSV and ZIP reconcile with that one map. The known PDF Oxide merge-link failure is fixed or handled by a qualified Rust implementation.
3. Signed/encrypted/inconclusive admission, permission policy, original and prior-build integrity, protected storage, recovery, cancellation, redaction and output validation pass their independent checks. PDF-03/06/07/08 and other open feature gates remain open unless their own stated acceptance checks pass.
4. Memory, CPU, disk and concurrency limits are measured on realistic large inputs. Raw Tauri IPC and parser allocations are bounded or an operationally enforceable scoped-file design is proved. Disk-full, process interruption, power-loss-equivalent and file-race checks show zero or one complete publication; timeout is not treated as cancellation or an automatic retry trigger.
5. A final source build passes real Apple Silicon, Intel Mac and Windows x64 compile/package, clean-install, reopen, native input/render responsiveness, PDF export/Save/print and upgrade/recovery checks. Browser screenshots at the supplied reference viewports verify that existing light/dark layouts and controls remain intact. Missing target evidence blocks that target's release claim.
6. A package inspection and native process check show no required Python, PyInstaller, PyMuPDF, Python PDF worker or Rust PDF child process. The complete Rust path works offline with the packaged Tesseract models and fonts where required.

If any gate fails, retain the Python default and the restricted Rust pilot. Do not partially enable a user-facing PDF route or remove a feature to meet a date. The release should use a reversible backend selection only while storage formats remain compatible; test upgrade and rollback with synthetic backups before migrating real user data. Never direct two writers at one store.

## Immediate execution order

1. Produce a machine-readable route/operation inventory and shared parity corpus, starting with the unresolved merge-link, general admission/signature, vault format and page-map contracts. This exposes PDF Oxide gaps before broad implementation.
2. Build Rust storage/vault, document revision/history and durable-job ownership so PDF writes have a safe destination. Keep the single-writer boundary explicit.
3. Implement packages 2–6 against the frozen corpus, resolving gaps within Rust and retaining explicit refusals in opt-in mode. Add exact-map parity before bundle writing.
4. Run the full cutover gate, update `RUST_REQUIREMENTS_MATRIX.md` and `ACCEPTANCE_TESTS.md`, then switch the default and remove shipped Python dependencies in the same release change.
