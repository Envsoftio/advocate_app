# Open PDF Studio source review for CourtBundle PDF editing

For the comparison with Folio, PDF.js, `pdf-lib`, PDF Forge, MuPDF.js and `pdfium-render`, and the requirements-to-engine plan, see [PDF editor engine and UX feasibility](PDF_EDITOR_ENGINE_AND_UX_FEASIBILITY.md).

**Reviewed:** 21 October 2026. **Upstream snapshot:** [`a22ba7a5d332aad806ae0bf658551cb846a6f849`](https://github.com/OpenAEC-Foundation/open-pdf-studio/tree/a22ba7a5d332aad806ae0bf658551cb846a6f849). This is a targeted source review of rendering, text editing, saving and their tests, not an executed benchmark or a complete audit of every upstream feature. No upstream code has been copied.

## Decision

Improve the Vue/PDF.js editor and current PyMuPDF working-copy engine first. Borrow **design techniques** from Open PDF Studio, then compare rendered performance on our own synthetic A4 text, scan, mixed-script, rotated and long-bundle fixtures. Add PDFium only if a measured, user-visible rendering benefit exceeds the packaging, licensing, memory and second-engine costs. Reuse upstream source only after a file-level license review and an isolated prototype.

The current repository has separate evidence for backend throughput and browser UI behavior. Its [1,000-page baseline](POC_ACCEPTANCE_TESTS.md#repeatable-scale-baseline) measures import, build and search, not time to first visible PDF page, sharp zoom, edit latency or native save. The latter metrics are currently unknown. Existing editor paths are [PdfViewer.vue](../frontend/src/components/PdfViewer.vue), [api.ts](../frontend/src/lib/api.ts), [pdf_ops.py](../backend/app/pdf_ops.py), and [native_save.rs](../frontend/src-tauri/src/native_save.rs).

## Highest-value CourtBundle work

### Borrowing the editing interaction

The upstream interaction is a pipeline, not a standalone engine. Its [`manager.js`](https://github.com/OpenAEC-Foundation/open-pdf-studio/blob/a22ba7a5d332aad806ae0bf658551cb846a6f849/open-pdf-studio/js/tools/manager.js) selects and dispatches tools; [`tool-context.js`](https://github.com/OpenAEC-Foundation/open-pdf-studio/blob/a22ba7a5d332aad806ae0bf658551cb846a6f849/open-pdf-studio/js/tools/tool-context.js) converts pointers into page coordinates; [`text-edit-tool.js`](https://github.com/OpenAEC-Foundation/open-pdf-studio/blob/a22ba7a5d332aad806ae0bf658551cb846a6f849/open-pdf-studio/js/tools/text-edit-tool.js) handles native text selection and an inline editor; [`undo-manager.js`](https://github.com/OpenAEC-Foundation/open-pdf-studio/blob/a22ba7a5d332aad806ae0bf658551cb846a6f849/open-pdf-studio/js/core/undo-manager.js) records client-side commands; and `saver.js` serializes the PDF. The tools read global app state and DOM elements, and the undo manager imports SolidJS. Copying this chain into Vue would pull in the foreign state, canvas, annotation and save architecture.

Use its interaction design as a reference for a **Vue editing workspace**: a single active tool, page-coordinate service, selectable objects with handles, inline preview, properties inspector, and explicit Apply/Cancel. For reusable source candidates, isolate pure geometry, selection and content-stream helpers behind a typed adapter. Do not copy `manager.js`, `tool-context.js`, `text-edit-tool.js`, `undo-manager.js` or `saver.js` wholesale. The backend remains authoritative for revision history and PDF writes. A Vue draft can be freely moved or resized; Apply sends one typed edit command with the expected document revision and page identity; the backend returns the new revision and actual method used.

Also distinguish upstream [`proofreading-mode.js`](https://github.com/OpenAEC-Foundation/open-pdf-studio/blob/a22ba7a5d332aad806ae0bf658551cb846a6f849/open-pdf-studio/js/tools/proofreading-mode.js) from native text editing: its insertion, replacement and deletion gestures create correction annotations through [`proofreading-apply.js`](https://github.com/OpenAEC-Foundation/open-pdf-studio/blob/a22ba7a5d332aad806ae0bf658551cb846a6f849/open-pdf-studio/js/annotations/corrections/proofreading-apply.js). That is useful for reviewed markup, but should not be presented as changed PDF source text.

### One workspace for every current PDF tool

The editor redesign must cover the existing tools together, rather than polish only text editing. [The current viewer](../frontend/src/components/PdfViewer.vue) has separate booleans and panels for Add text, Edit text, Redact, Notes (images/highlights/comments), Links, and Output marks; page actions sit in the same toolbar. A single typed `activeTool` should control pointer behavior, selection, keyboard shortcuts, inspector content and Cancel. The common interaction is **choose tool → select or draw on the page → adjust a live draft → inspect the outcome/policy → Apply or Cancel → reopen/verify**. Each tool owns a typed draft and validation rules; the workspace owns document/revision identity, coordinate conversion and busy/error state.

| Tool | Current behavior to preserve | Unified workspace behavior and contract |
| --- | --- | --- |
| Add/edit text | ASCII overlay and bounded native span replacement; OCR remains a searchable layer. | Inline editable preview, font/fit feedback and explicit classification of the resulting PDF change. Fail visibly if the selected native edit cannot be performed. |
| Insert image | Revision-anchored image overlay flattened into a new build. | Select image, place/resize it with handles, show actual page preview, then save one undoable operation. Clarify whether the user expects the working PDF itself or only generated output to contain it. |
| Highlight/comment | Private review annotations omitted from filing output by default. | Select a text/region and edit in an inspector. Keep the inclusion policy visible; do not silently flatten private comments into a filing PDF. |
| Link | Reviewed source rectangle with internal matter target or allowed external URI; revisions can make it unresolved. | Drag/select the source region, choose and preview destination, then verify the link in volume and combined PDF output. Keep unresolved links visible after later edits. |
| Redact | A destructive working-copy revision after a reviewed rectangle; broader security acceptance is open. | Dedicated Mark → Review → Apply flow with a separate warning and post-save verification. It must not share a generic overlay Apply handler. Prior originals/revisions/exports remain separately controlled. |
| Stamp/marks | Existing watermarks, timestamps, Bates and annexure labels are output settings, not a general user-placed reusable stamp on the working PDF. | Keep **output marks** in Build settings with on-page preview. A true user-placed stamp is a separate feature requiring its own asset/preset model, placement/resize UI, inclusion policy, revision behavior and PDF round-trip tests. Do not label the current output-mark panel as arbitrary stamping. |
| Page operations | Rotate, reorder, insert, replace, crop, split and extract follow working-copy/page-output rules. | Put page actions in a page-specific command area; use thumbnail drag/drop and an explicit before/after preview. Preserve shared page-map and revision rules. |

Suggested Vue module boundary: `PdfWorkspace` (layout/navigation), `PdfCanvas` (render and coordinate service), `EditToolController` (one active tool and its draft), `SelectionOverlay` (handles and preview), per-tool inspectors, and typed API adapters. Existing backend mutation endpoints remain authoritative while the interface is changed. This is an architecture target, not a claim that the current code already has this separation.

1. **Measure the actual editor journey.** In a disposable synthetic matter, record file bytes, time to first page, time to sharp page, page switch, zoom, thumbnail completion, edit preview, save/reopen, peak WebView and sidecar memory. Run warm and cold cases in browser and packaged native app. Include A4 text, 300-DPI scans, Hindi/English mixed text, rotated pages, and a 300+ page working PDF. Keep per-stage timings so transport, parsing, rendering and save are not conflated.
2. **Improve the Vue render pipeline.** Today [PdfViewer.vue](../frontend/src/components/PdfViewer.vue) fetches the entire PDF into a `Uint8Array`, cancels and serializes page renders, renders seven thumbnails sequentially, and awaits thumbnail completion during load. Those are source-observed candidates, not measured bottlenecks. Make the visible page independent of thumbnails, retain a last-good image during zoom, and use generation/revision tokens for all async responses. Test fast page switching, rapid zoom, document switching and revision changes before claiming improvement.
3. **Build a bounded text-edit prototype.** Compare current PyMuPDF span replacement with a strictly gated content-stream approach on synthetic fonts, subset fonts, ligatures, rotated text, CJK/Devanagari, OCR scans, links and overlapping content. Report `native-content-edit`, `visual-replacement`, `ocr-layer-correction`, or `unsupported` explicitly. Never publish a new revision when the chosen method cannot meet its contract.
4. **Use professional round-trip acceptance.** Save, reopen with PyMuPDF and an independent reader where practical, compare selected rendered regions and extracted text, check navigation/links and unselected page content, Undo/Redo, build a bundle, then verify shared page-map destinations. Include repeated edits/saves and failed-write recovery.

**Implementation gate:** Choose PDFium only after the same supported hardware, same fixture bytes, same scale and device pixel ratio, cold/warm cache separation, and end-to-end time-to-visible comparison. Set the pass budget before choosing an engine; do not claim a speedup from upstream's CAD-oriented examples or a backend-only benchmark.
