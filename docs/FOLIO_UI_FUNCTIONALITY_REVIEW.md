# Folio UI and functionality review

## Independent annotation controls — 22 October 2026 follow-up

The screenshot and Folio's current feature list show separate Annotate controls for Highlight, Comment, Draw, Box, Ellipse, Line and Arrow, plus visual check/cross/date stamps. CourtBundle groups viewer controls under Edit, Annotate, Stamps, Pages and Output. Added text, drawing, shapes, image/stamp and redaction marks now remain separate revision-anchored objects after addition: select, drag, resize or Delete/Backspace each one. Undo/Redo and portable matter restore retain them. Existing reviewed links use the same direct selection controls.

The layer has an explicit output scope. Highlights and comments remain private; added text, drawing, shapes, visual stamps, images and redaction marks are flattened into Save copy and new filing bundles. Redaction marks remove content in those generated PDFs, while the raw working revision and imported originals still contain it; the UI says this at the point of use. Stamps do not claim form filling or verified signatures. There is no Whiteout control. Native Mac/Windows interaction and an actual signing workflow remain open. This follows Folio's interaction pattern without copying its runtime or PDF writer.

## Implementation follow-up — 22 October 2026

Implemented the coherent reader slice: shared working/output rendering, virtual page surfaces, continuous/single-page modes, explicit magnification, session positions, Back, occurrence search, source outline and safe native links. Added a document-scoped private comment list, keyboard tab navigation, atomic batch page organization and actual-page crop. Existing text-edit cards and backend engines are retained; no Folio source code or PDF writer was copied.

The completion follow-up implements the remaining recommended reader/page-management features: protected-store reading-position persistence, actual insertion/replacement previews, a virtual full-screen thumbnail rail, shared keyboard help, exact-revision Save copy, named matter-wide Undo/Redo descriptions and authenticated range loading for working/generated PDFs above the former 25 MiB UI cap. The organizer mounts at most 24 thumbnails per grid; continuous reading mounts a viewport-sized window (including very small pages), with a 32-million-pixel aggregate displayed raster target. Rendering and old/new bitmap swaps temporarily add staging buffers. The full-screen rail renders only nearby rows and releases departed thumbnail bitmaps. These limits bound application-owned canvases, not every allocation in PDF.js or a native WebView. Native Mac navigation/restart/Save checks and synthetic performance measurements are now recorded in [acceptance section AX](POC_ACCEPTANCE_TESTS.md#ax-folio-completion-follow-up--22-october-2026). Existing PDF/native acceptance tickets remain open until their complete device criteria are met.

After feedback from a running dev build, the edit-tool presentation was clarified without adopting Folio's text editor: Add text has clearer placement and shortcut guidance, image placement names its destination in plain language, and Redact shows an explicit mark/review/apply sequence with a redraw action. Redaction checks the current working revision and uses the same signature-review challenge as text edits; a stale revision still returns 409 and asks the user to redraw rather than silently applying to another revision. A later editing follow-up made the PDFium capability an explicit **Edit whole paragraph** action on supported text, rather than a choice of engine names. Single-run replacement now checks the actual footprint of each line instead of treating a distant right-column object as a full-width blocker. Text drag supports both page axes and applies only to a clear destination; actual collisions remain rejected. The source dev server was observed serving the updated labels, and the running Python backend used Uvicorn reload mode. Synthetic verification before the later editing follow-up: 205 backend tests, 41 frontend unit tests, and focused Chrome journeys for Add text, paragraph editing, redaction (including the signature-status race), rotated redaction, and image/review annotations. The existing browser/dev session may need a window reload to display newly mounted tool panels; packaged native builds require a separate rebuild.

An applied redaction now has a persistent selectable outline in the Redact tool. Removing it creates a new working revision from the retained pre-redaction source for the outlined area, including complete text spans touched by the original mark. Later content inside the outline is replaced; later content outside it remains. Page reorder, insert, delete, replacement, crop or rotation after redaction disables selective restoration rather than risk mapping the saved content to the wrong page. Synthetic tests cover later edits, rotated pages, another redacted secret, Undo/Redo, structural invalidation and portable backup; native interaction and broader security acceptance remain open.

## What creates Folio's visual polish

**[Certain] Its screen hierarchy keeps the document dominant.** File actions and history stay at the top; the selected task changes a second row of tools; pages live in a dedicated rail; page position and zoom stay at the bottom. The PDF has a quiet gray surround and a clear page edge. The live Pages view had substantial empty toolbar space instead of exposing every operation simultaneously. See the [shell markup](https://github.com/doktorigi/folio/blob/b366581f27953a18b057a15d7c3fb028011e8eb6/index.html#L55) and [style tokens](https://github.com/doktorigi/folio/blob/b366581f27953a18b057a15d7c3fb028011e8eb6/src/style.css#L3).

**[Likely] The transferable lesson is placement and restraint.** Keep common actions in stable positions, expose only relevant properties, use one visual language for active tools and selection, and reserve most of the window for paper. Folio itself still shows font/color/stroke controls on its Pages tab; we can make that row more contextual.

Recommended CourtBundle arrangement:

| Region | Contents and behavior |
| --- | --- |
| Document header | Document name, working-copy/revision or generated-build identity, undo/redo, explicit Save copy or export action, focus/full-window control. Do not label persisted working revisions as unsaved just because they have not been exported. |
| Task row | Retain our Edit, Review, Pages and Output groups. Show the active tool and relevant settings. Keep the current text-edit cards and Apply/Cancel flow. |
| Left navigation | Distinguish **Documents**, **Pages** and **Outline**. Use switchable or collapsible panels so two thumbnail rails do not consume the paper area unnecessarily. Preserve the existing document-order controls. |
| Document area | Single-page and continuous reading modes; consistent page gaps; precise text, link and overlay alignment; focused-page editing. |
| Optional right panel | Find results, comments or selected-object properties, shown when needed. Preserve private-review versus filing-output policy. |
| Bottom navigation | Physical page position, optional separately labelled printed/Bates value, explicit zoom mode/value and background-operation status. |

This is a proposed refinement of the existing workspace, not a second editor or a new preparation mode.

## What should not be copied

**[Certain] Folio's rendering is lazy, but its page list is not virtualized.** It creates a DOM container and thumbnail for every page, rebuilds the list on zoom, and finds the current page through a linear geometry scan. Its refresh path creates another PDF.js document without destroying the previous one; painting lacks the cancellation/generation guards already present in CourtBundle. The source shows these mechanisms; it does not establish a measured memory leak or performance failure. See [refresh/render](https://github.com/doktorigi/folio/blob/b366581f27953a18b057a15d7c3fb028011e8eb6/src/main.js#L80).

**[Likely] Three source patterns deserve regression tests before any adaptation:** search hits appear to survive page mutations or opening another file; switching ribbons hides controls without clearing the active tool; a file drop on a thumbnail can also enter the page-reorder handler. These are unconfirmed runtime risks, not reproduced defects. See [search navigation](https://github.com/doktorigi/folio/blob/b366581f27953a18b057a15d7c3fb028011e8eb6/src/main.js#L884), [ribbon switching](https://github.com/doktorigi/folio/blob/b366581f27953a18b057a15d7c3fb028011e8eb6/src/main.js#L797), and [thumbnail drop](https://github.com/doktorigi/folio/blob/b366581f27953a18b057a15d7c3fb028011e8eb6/src/main.js#L147).

**[Certain] The audited repository has 15 Node PDF-helper tests, without browser/native UI test files in the inspected tree.** Its source includes a Windows release workflow, not evidence of CourtBundle's macOS/Windows acceptance matrix. Its Tauri shell does not supply our native save/sidecar/storage workflow. See [tests](https://github.com/doktorigi/folio/tree/b366581f27953a18b057a15d7c3fb028011e8eb6/test) and [native entry point](https://github.com/doktorigi/folio/blob/b366581f27953a18b057a15d7c3fb028011e8eb6/src-tauri/src/main.rs).

Do not copy Folio's in-memory page-index authority, PDF writer, raster printing, fixed lossy compression, or signing assumptions into the viewer-polish work. Its editing tools are outside this review. Core processing remains offline; imported originals and CourtBundle's deterministic page map remain authoritative.

The [audited LICENSE](https://github.com/doktorigi/folio/blob/b366581f27953a18b057a15d7c3fb028011e8eb6/LICENSE) is MIT and requires retention of its notice for copied substantial code. Record exact files and dependency notices if code is reused. Reimplementing the interaction patterns within Vue avoids importing the whole vanilla-JavaScript application.

## Implementation sequence

This was the proposed sequence. The implementation follow-up above identifies delivered scope; the acceptance log identifies tested scope. The complete acceptance gates below are not all closed. They refine the reader/workspace direction already in the [project handoff](../CourtBundle_Project_Context_and_Handoff.md).

| Order | Concrete scope | Acceptance gate |
| --- | --- | --- |
| 1. Shared reader foundation | Extract PDF.js document lifetime, viewport geometry and render scheduling from `PdfViewer.vue`; mount the same reader in `ExportPdfReview.vue` with editing disabled. Preserve existing editing UI. | Working and generated PDFs render/search/select consistently; closing/switching cancels old work; build/revision identity cannot be confused; existing editing and page-operation journeys still pass. |
| 2. Reading and navigation | Continuous and single-page modes, explicit fit/numeric zoom, stable zoom anchor, reading-position memory and Back navigation; consolidate header/ribbon/footer. | Repeated zoom and pane changes keep the viewed passage visible; long and mixed-size documents stay navigable; edits affect the intended focused page; changing revisions invalidates obsolete positions safely. |
| 3. Search and native navigation | Occurrence results and geometry, active-match count, keyboard navigation, source outlines and safe internal/external PDF links. | Multiple hits on one page work; phrases split across text runs highlight correctly; Hindi/English and rotated pages are covered; page mutation/document switch never reuses stale hit destinations. |
| 4. Visual page management | Organizer grid, explicit selection, keyboard/drag ordering, batch rotate/delete, insertion preview and actual-page crop. Reuse existing operations; add an atomic batch endpoint for rotate/delete. | Only selected pages change; cancel does nothing; one committed batch is one undo action; originals remain identical; affected links/bookmarks/marks follow current revision policy; export/reopen order and dimensions agree. |
| 5. Review and finish | Comment navigation, concise state/error messages, shortcut help, focus/ARIA improvements, native Save integration and measured large-output review. | No silent download/save failures; focus survives dialogs/updates; private notes obey output policy; keyboard-only journeys and target-device visual/performance checks pass. |

The first useful delivery should be a coherent reader slice: shared rendering, continuous reading and explicit zoom, with the current editor retained. Search precision and organizer work should follow that foundation. Forms, certificate signing, Office conversion and new editing engines should not be bundled into this UI task.

Suggested internal boundaries are a reader component, document-source adapter, render scheduler, viewport/coordinate service, search controller and page-selection model. These are proposed responsibilities, not a requirement to introduce a new state-management framework. Backend page/text/image operations continue to commit through the existing working-copy transaction. Rendering knows the document and revision; output numbering still comes solely from `backend/app/engine.py`.

At the review baseline, rotate/delete endpoints accepted one page per transaction. The implementation adds a revision-checked atomic batch endpoint. A multi-page organizer action needs a small backend extension that validates the complete selection against one revision and publishes one history event. Repeated single-page HTTP calls would not satisfy atomic cancellation/failure or one-step Undo.

For continuous reading, render visible pages first, prefetch a small neighboring window, evict offscreen bitmaps under an explicit byte budget and virtualize thumbnails/page containers. Keep all page overlays on the exact viewport transform. Persist only necessary reading-state metadata through the appropriate existing storage boundary; do not cache confidential PDF text or bytes in a new browser store.

## What a polished result must prove

Visual similarity alone is insufficient. Use synthetic native-text, English/Hindi, scanned, mixed-size and rotated documents, plus long bundles and existing signature-risk fixtures.

1. **Visual stability:** Inspect supported window sizes and 90/100/110/125% UI scaling in light/dark themes. Toolbars remain reachable; page content is not covered by dialogs; selection, caret, highlight and link geometry remain aligned through zoom and rotation. Compare the same fixtures at the same viewport.
2. **Navigation correctness:** Test page jump, continuous scroll, thumbnails, outline, occurrence search and Back. Switch documents and mutate pages while render/search work is pending. A late result must never display or select a previous document/revision.
3. **Operation fidelity:** Reopen working and generated PDFs after organize/crop/insert operations. Check page order, dimensions, source hashes, undo/redo and mark/link policies. Every new volume/index rule needs pytest against the deterministic page map; a UI organizer must not invent numbering rules.
4. **Measured responsiveness:** Record cold/warm first visible page, sharp-page latency, page-jump latency, zoom completion, search completion, peak memory and memory after repeated open/close on 10-, 100- and 1,000-page fixtures. A sample aim for warm navigation is under 200 ms to feedback and under 500 ms to a sharp ordinary page on a named reference device; these are proposed targets, not measurements or supported-device promises. Set resource budgets from native measurements.
5. **Accessible operation:** Complete page navigation, selection, reorder, search and dialog cancellation without a mouse. Check roving tab focus, selected states, announcements and focus restoration. Retain typed page-range alternatives for visual operations.
6. **Native acceptance:** Exercise macOS WKWebView and Windows WebView2 on the supported matrix, including offline startup and native Save/cancellation/failure/reopen. Browser checks do not close NAT-01/02/03 or pending PDF acceptance.

Existing starting points are [workspace-design.spec.ts](../frontend/e2e/workspace-design.spec.ts), [journey.spec.ts](../frontend/e2e/journey.spec.ts), the page-operation backend tests, and the native verification checklists. Extend behavior-focused journeys for each new capability; do not mark the overall editor perfected because a stylesheet or browser build passes.
