# PDF editor: engine and user experience feasibility

**Reviewed:** 21 October 2026. This is a source and requirements review, not a claim that any candidate was installed, benchmarked, or validated on CourtBundle fixtures. Read with the [Open PDF Studio source review](OPEN_PDF_STUDIO_SOURCE_REVIEW.md), the [product handoff](../CourtBundle_Project_Context_and_Handoff.md), the [implementation backlog](IMPLEMENTATION_TASKS.md), and [acceptance evidence](POC_ACCEPTANCE_TESTS.md).

## Decision

**[Certain] No listed project is a drop-in engine for the whole first-release promise.** Keep a single CourtBundle editing workspace in Vue and a single authoritative working-copy/revision/build path in the local Python sidecar. Rebuild the viewer interaction around a shared selection and tool model. Use PDF.js for display and text selection initially; keep PyMuPDF for committed edits, OCR, page operations, redaction, and final export while evaluating narrow replacements against fixtures. Evaluate PDFium paragraph editing as an isolated spike, not an automatic fallback to whiteout. Keep the deterministic build page map in `backend/app/engine.py`.

**[Likely] The immediate usability gain is in rendering and interaction scheduling, not replacing the PDF writer.** At the start of this review, [the viewer](../frontend/src/components/PdfViewer.vue) downloaded whole PDF bytes when loading a revision, awaited thumbnails during load, serialized renders, and mixed multiple editing panels and pointer modes in one component. The first three behaviors have since been changed as recorded below; target-device performance still needs measurement. The existing [1,000-page baseline](POC_ACCEPTANCE_TESTS.md#repeatable-scale-baseline) is not a viewer benchmark. Existing backend functions are real but do not establish a good user experience or broad editing coverage.

## Current coupling assessment

**Verdict: mixed, with a tightly coupled frontend editor.** Vue and Python communicate over local HTTP through [`api.ts`](../frontend/src/lib/api.ts), and the Python backend owns PDF bytes and revisions. That boundary allows the rendering UI to change without replacing the backend. However, [`PdfViewer.vue`](../frontend/src/components/PdfViewer.vue) remains a large component combining PDF.js lifecycle, thumbnails, zoom, pointer geometry, modes, review annotations, links, marks, redaction, text-edit requests and operation-specific notices. It constructs endpoint paths and payloads itself. [`App.vue`](../frontend/src/App.vue) owns page-tool dialog, OCR jobs, document refresh and editor navigation, so a single edit can involve several component callbacks and reloads. This is **high internal UI coupling**, not loose coupling merely because the backend is a separate process.

Backend coupling is moderate. [`main.py`](../backend/app/main.py) exposes separate page-edit routes but centralizes PDF mutations through `edit_working_copy()`: it locks the matter, copies the current revision, invokes an operation, commits the new path/revision, and discards failed candidates. [`pdf_ops.py`](../backend/app/pdf_ops.py) contains the PyMuPDF edit functions. This makes replacing one edit method feasible while preserving storage and history. The current routes are nevertheless tied directly to PyMuPDF-oriented operation functions and schemas; there is no provider-neutral `PdfEditEngine` or unified edit-result contract. In addition, image overlays, private annotations and reviewed links are stored as revision-anchored application data and applied or excluded during [`engine.py`](../backend/app/engine.py) builds, while text/page/redaction operations mutate PDF working copies. A new library must honor these distinct persistence and export policies.

**Practical implication:** start by extracting renderer, coordinate conversion, tool state and typed API methods from the Vue component. Introduce an edit-engine interface only for the capability being trialed (for example, paragraph replacement), inside the existing backend revision transaction. Keep the existing route/build policies until a fixture proves a different representation is correct. Adding several writers directly to Vue would tighten coupling further and make undo, save, security and bundle output harder to reconcile.

## Integration shape

**21 October 2026 implementation note:** The current Vue viewer has Edit/Review/Pages/Output tool groups, document Find, visible thumbnails, direct page text entry, and in-view controls after drawing highlight, comment, redaction or link regions. The backend remains the owner of working-copy revisions. This is an interaction improvement, not completion of the refactoring or target-device acceptance below. Whiteout is not implemented as a separate operation; the redaction tool must not be presented as a harmless visual cover.

1. **One editor model.** Create a Vue workspace with one active tool (`select`, `text`, `image`, `highlight`, `comment`, `link`, `stamp`, `redact`, `page`), page coordinate service, selected object, typed draft, inspector and Apply/Cancel. Do not encode mode using independent booleans. Separate ordinary editing from redaction's Mark → Review → Apply state machine. Surface whether an edit changes PDF page content, creates a review annotation, or appears only in generated output.
2. **One render lifecycle.** Keep a parsed PDF.js document for the exact document/revision; render the visible page ahead of thumbnails, reuse a last-good bitmap while sharpening, abort or discard stale render generations, cap pixels and cache bytes, and release canvases/documents. Preserve text and annotation layers at the same viewport transform. Only consider PDFium after measuring this version on macOS and Windows fixtures.
3. **One commit contract.** Frontend sends a typed operation with `document_id`, `expected_revision`, stable page identity, PDF-space geometry, and tool-specific payload. Backend validates against that revision, writes a new encrypted working copy atomically, records undo/provenance, and returns new revision, actual edit method and warnings. Redaction and signatures have their own stronger review gates. All bundle outputs continue through `engine.py`'s page map.
4. **Pluggable experimental text adapter.** Keep paragraph editing behind a backend interface or isolated native worker; input bytes/selected paragraph and requested text, output bytes or explicit unsupported. A fallback to visual overlay must be a *user-visible different operation*. Importing PDF Forge's browser PDFium module directly into the Vue process would add a second writer and bypass the sidecar's revision/storage policy.
5. **No release-by-feature-list.** A tool is done only after committed edit, reopen, undo/redo, export, failure recovery, and supported target-device inspection all pass for its stated scope. Record known unsupported PDF constructs in the UI before Apply.

## Execution order and gates

1. **Capture current failures on synthetic matters.** Reproduce the user's top broken workflows and record expected versus actual result, file type/page/rotation, OS/WebView, console/sidecar error and revision. Build a fixture set spanning normal A4 native text, 300-DPI scan, English/Hindi mixed text, subset fonts, forms, links, rotated pages, signed-input indicators and a long bundle. No confidential documents.
2. **Ship the Vue workspace and render scheduling repair.** Start with page navigation, zoom, visible-page priority and a shared selection/coordinate layer. Then migrate existing text, image, highlight/comment, link, page and mark tools, preserving their existing backend revision/export policies. Require keyboard, pointer and target-device checks on Mac/Windows.
3. **Run a bounded paragraph-edit comparison.** Prototype current PyMuPDF method and PDF Forge/PDFium approach on the same fixture bytes. Capture time, peak memory, byte growth, font substitution, unsupported rate, Unicode search, extraction order, before/after pixels outside edit bounds, links/forms, repeated save/reopen and undo. Keep the candidate only if it materially improves supported cases without changing unselected content or breaking the build. No silent fallback.
4. **Complete the separately blocked tools.** Obtain reviewed edit/OCR and Office fixtures, then scope `PDF-07/08`; finish `PDF-10` security/retention/device checks; complete print/scanner/signature decisions. UI polishing cannot substitute for these acceptance gates.

**Performance gate:** Set thresholds before changing engines and measure the entire click-to-visible/edit-to-reopen journey on the same hardware, bytes, viewport and device pixel ratio, with cold and warm runs separately. Report p50/p95 and peak memory; compare current build, repaired PDF.js build and any PDFium prototype. Do not infer speed from a candidate's README or another product's benchmark.

**Licensing gate:** Record exact source files and transitive notices before reuse. Open PDF Studio is LGPL-3.0; Folio/PDF Forge/`pdf-lib` are MIT; PDF.js is Apache-2.0; `pdfium-render` is MIT/Apache-2.0 but ships without PDFium; MuPDF.js and current PyMuPDF have AGPL/commercial terms. Distribution needs a deliberate license review; this document is engineering guidance, not legal advice.

## Branch implementation checkpoint — 21 October 2026

The first editing pass now uses one Vue `activeTool` state, offscreen PDF.js page rendering that preserves the last visible canvas during page switches, a 16-megapixel raster allocation cap, independent thumbnail rendering with a small per-revision cache, and a PDF.js selectable text layer. Undo/Redo are accessible from the viewer. Text dragging now requires an explicit Apply/Cancel. Existing text replacement and movement report their actual remove-and-redraw method. A PNG/JPEG can be previewed and inserted into a new working-copy revision or retained as the existing build-only overlay; the working-copy path uses `edit_working_copy()` and rotated-page coordinate mapping. One synthetic rotated-page smoke check and one focused HTTP test for revision/undo/original preservation and combined-PDF output passed; `vue-tsc` and the Vite build passed. Native runtime placement and visual fidelity remain unverified.

No PDFium writer was added. `@embedpdf/pdfium` and a PDFium runtime are absent locally, and an npm registry lookup failed with `ENOTFOUND`. The PDF Forge paragraph trial therefore remains open; its code has not been copied or represented as working. The PDF editing PRD remains incomplete, especially Unicode and paragraph editing, OCR correction, reusable editable stamps, form/signature workflows, and the remaining native acceptance work.

## Continued implementation — 21 October 2026

The viewer now loads the exact working revision through PDF.js's authenticated URL source, allowing range requests where the local response supports them and avoiding an extra full-file `Uint8Array` allocation. The PDF endpoint rejects a stale requested revision. Pending PDF.js loads are destroyed on document changes, visible page work cancels thumbnail work, and editing overlays are hidden while their page/revision bitmap is stale. A direct page-number field was added.

The [PDFium paragraph trial](PDFIUM_PARAGRAPH_TRIAL.md) now runs with `pypdfium2` inside the Python sidecar's existing working-revision transaction. It adapts PDF Forge's paragraph object-edit approach, reflows selected multi-line native text, verifies the proposed PDF, and never silently falls back to visual replacement. Five focused synthetic API tests, including combined export, link-overlap rejection and preservation of repeated text elsewhere, passed. The Vue production build, Rust check, frozen Apple Silicon sidecar status endpoint and local macOS arm64 app build passed. A synthetic Chrome browser journey completed a trial edit and matter search; it found a preview typing race, which was fixed. Native UI, Intel/Windows and broader fixture acceptance remain open. This supersedes the earlier worker-only checkpoint above.

## Folio interaction pass — 22 October 2026

The user's request to use Folio led to a focused interaction experiment. A directly editable page draft and drag handle were built, then withdrawn after the user reported that the prior floating Add text card was easier to use and the draft text was unreadable. Add text again uses that card with a black page preview and explicit dark input text. Thumbnails collapse while an editing tool is active and return in Select mode. The saved edit still goes through CourtBundle's local working-copy revision and Undo path. This is an independent Vue implementation informed by [Folio's MIT source](https://github.com/doktorigi/folio/tree/b366581f27953a18b057a15d7c3fb028011e8eb6); Folio's runtime and `pdf-lib` writer were not embedded.

The prior `/pages/text-overlay` report named `acknowledge_signature_risk` as an invalid boolean. The common JSON schema now treats any value other than literal `true` as unacknowledged. A signature-risk document therefore still blocks editing with 409 unless the user explicitly approves the operation. Add text now fetches current local document status before its POST, so known risks prompt first; a specific 409 caused by a status race still prompts and retries with boolean `true` only after fresh confirmation. Other Add text errors appear in the app toast while the draft stays intact; validation no longer expands the floating card. The user's `03_affidavit` failure supplied the exact 409 detail; the reason its earlier client-side document status and server decision differed has not been established. A dark-theme CSS override was corrected so the card has a white input and black text. Full backend pytest passed (159), Vue build and 10 Vitest tests passed, and the full synthetic Chrome suite passed (42, one protected-vault test intentionally skipped) before the status precheck. A later focused Chrome check passed the dark-mode text, current-status approval before POST, signature-conflict retry and toast-on-error cases. A frozen Apple Silicon sidecar smoke used malformed acknowledgment on a synthetic unsigned document, then completed OCR, compression, export and protected backup checks. The local Mac app bundle was rebuilt with this frontend. The isolated native QA app reached first-time vault setup, so its editing UI was not exercised. The older `/Applications/CourtBundle POC.app` copy was not replaced. Folio-like handling for other tools and supported native-device acceptance remain open.

The subsequent navigation pass narrows Source documents to first-page preview cards with titles below, and adds a left page rail in full-screen view. The rail remains available while an editing tool is active, so changing pages no longer requires leaving Add text. The embedded viewer retains its horizontal strip. Preview PNGs come from an authenticated, revision-checked local endpoint that reads working copies; the frontend loads document previews as they enter view and renders page canvases lazily. No Folio runtime or PDF writer was imported. Synthetic browser coverage checks preview loading, full-screen page switching and drag/keyboard document ordering; performance on large native matters still needs measurement.
